============================================================
1. PROJECT VISION
============================================================

Build a local DNS security dataplane that receives DNS requests, validates
and parses them, normalizes domain names, evaluates security policy and
threat intelligence, optionally performs lightweight anomaly analysis,
uses a bounded TTL-aware cache, forwards permitted queries to an upstream
resolver, returns valid responses, and emits structured operational/security
telemetry.

The project must behave like a small network appliance rather than a
collection of unrelated demonstrations.

============================================================

DO NOT TURN THIS INTO:

    - a full recursive resolver
    - a complete authoritative DNS server
    - a complete IDS/IPS
    - a complete browser ad blocker
    - a complete DoH/DoT proxy
    - a full DNSSEC implementation
    - a general-purpose firewall
    - an ML showcase
    - a giant dashboard

Do not claim production readiness.

The project is a serious engineering prototype and experimental dataplane
unless substantially stronger validation later justifies a narrower claim.

============================================================
9. DNS PARSER SECURITY MODEL
============================================================

The parser receives attacker-controlled bytes.

Treat every byte as untrusted.

VALIDATION MUST COVER

    minimum packet length
    header availability
    field bounds
    QDCOUNT limits
    label length <= protocol limit
    total name length limits
    compression-pointer bounds
    compression-pointer loop protection
    supported opcode
    supported class/type policy
    maximum packet size
    malformed termination
    truncated input

PARSER RULE

    Never read before proving the bytes exist.

    Never follow an unbounded pointer chain.

    Never trust counts from the packet.

    Never allocate based on unbounded attacker-controlled values.

PARSER OUTPUT

Use a structured internal representation rather than passing raw offsets
through the whole application.

============================================================
11. DECISION ENGINE
============================================================

Every query receives exactly one primary decision.

RECOMMENDED PRECEDENCE

    1. INVALID / MALFORMED
           -> REJECT

    2. EXPLICIT ALLOWLIST
           -> ALLOW

    3. EXPLICIT BLOCK
           -> BLOCK

    4. PARENT-DOMAIN BLOCK
           -> BLOCK

    5. THREAT-INTELLIGENCE MATCH
           -> BLOCK or ALERT

    6. ANOMALY SIGNAL
           -> ALERT initially

    7. DEFAULT
           -> ALLOW / FORWARD

The precedence must be represented in code and tests.

Every security decision must be explainable.

Example:

    action:
        BLOCK

    reason:
        THREAT_INTELLIGENCE_MATCH

    category:
        MALWARE

    rule_id:
        feed-12345

    dataset_version:
        2026-09-01

    matcher:
        SUFFIX_TRIE


============================================================
12. ACTION MODEL
============================================================

ALLOW
    Forward query or return valid cached response.

BLOCK
    Return a controlled blocking DNS response.

SINKHOLE
    Return a controlled lab address for test environments.

ALERT_AND_ALLOW
    Record suspicious behavior but permit resolution.

REJECT
    Reject malformed/unsupported traffic.

Do not use real malicious infrastructure for testing.

Use reserved/documentation domains and controlled lab domains.

14. DOMAIN MATCHING ENGINE
============================================================

BASELINE

    std::unordered_set

SECURITY-CORRECT STRUCTURE

    reverse-label suffix trie

OPTIONAL RESEARCH IMPLEMENTATION

    Aho-Corasick

Important:

    Do NOT assume Aho-Corasick is superior for DNS suffix matching.

DNS suffix matching has domain-boundary semantics.

Rule:

    example.com

Must match:

    example.com
    www.example.com
    a.b.example.com

Must NOT match:

    notexample.com
    example.com.evil.test

EXPERIMENT

Compare:

    unordered_set
    suffix trie
    Aho-Corasick

At:

    10K
    50K
    100K
    500K
    1M where practical

Measure:

    lookup latency
    p50
    p95
    p99
    throughput
    memory
    construction time
    update time

============================================================

    bounded timeout
    controlled error behavior
    no indefinite blocking

40. EXPERIMENTAL RESEARCH QUESTIONS
============================================================

PRIMARY ENGINEERING QUESTION

Can a resource-conscious C++ DNS security dataplane on ARM64 provide
explainable DNS-layer security while maintaining predictable latency
under increasing rule-set size, concurrency, cache state, and inspection
complexity?

RQ1 — MATCHING

Which domain-matching structure provides the best latency/memory/update
trade-off for DNS suffix matching?

RQ2 — CACHE

How much can TTL-aware caching reduce upstream work and query latency?

RQ3 — SECURITY COST

What incremental processing cost is introduced by:

    policy only
    policy + threat intelligence
    policy + threat intelligence + anomaly detection

RQ4 — RULE SCALE

How does increasing rule-set size affect:

    memory
    startup
    lookup
    update time

RQ5 — CONCURRENCY

How does the dataplane behave as concurrency increases toward saturation?

RQ6 — RESILIENCE

How does the system degrade under upstream, policy, resource, and
control-plane failures?

RQ7 — CONTROL/DATA SEPARATION

What operational overhead does the control-plane boundary introduce,
and does it remain outside the normal DNS hot path?

RQ8 — I/O MODEL

Under controlled workloads, what performance/CPU trade-off exists between:

    blocking sockets
    epoll
    io_uring

The I/O experiment is optional and late-stage.

58. INTERVIEW STORY
============================================================

The final explanation should sound like this:

"I wanted to understand how a security function can be implemented close to
the network dataplane rather than as a high-level application. I built a
DNS security dataplane in C++ with a separate Go control plane and Python
offline intelligence pipeline.

The C++ engine receives DNS traffic, validates and parses untrusted packets,
normalizes domains, applies security policy, performs suffix matching,
caches eligible responses, forwards permitted queries upstream, and
generates structured events.

The important part was not only implementing the features. I treated the
project as a systems-engineering experiment. I fuzz-tested the DNS parser,
ran it under sanitizers, validated traffic with packet captures, injected
upstream and policy failures, profiled the dataplane, and measured the
effects of cache state, rule-set size, matcher choice, concurrency and
security inspection.

For the performance work, I kept the workload controlled and preserved raw
benchmark data rather than making unsupported performance claims. I also
investigated whether different I/O models actually changed the bottleneck
under the tested workload."

Do not memorize this word-for-word.

The final answer must reflect what was ACTUALLY implemented.

69. FINAL PRINCIPLES
============================================================

1. Correctness before optimization.

2. Security before convenience.

3. Benchmark before claiming performance.

4. Profile before optimizing.

5. Test malformed input.

6. Treat all network input as hostile.

7. Bound attacker-controlled resources.

9. Keep Python off the live path.

10. Keep Go off the DNS hot path.

11. Prefer simple designs before advanced ones.

14. Preserve raw experimental data.

15. Record the exact environment.

16. Keep negative results.

17. Every fixed bug gets a regression test.

18. Every important design choice gets documented.

19. Never confuse a prototype with production software.

20. Never invent performance or security results.

21. Build one coherent system.

22. BREAK IT ON PURPOSE.

23. MEASURE WHY IT BROKE.

24. FIX IT.

ARM64 DNS Security Dataplane — C++ / Go / Python

Designed and implemented a resource-conscious DNS security dataplane with a

updates, and lightweight DNS anomaly detection.

Engineering validation includes protocol regression testing, malformed-input
testing, fuzzing, sanitizer instrumentation, packet-level validation,
resource-limit testing, fault injection, profiling, and reproducible
performance experiments.

Research evaluation measures matcher design, cache behavior, rule-set
scaling, security-processing overhead, concurrency, anomaly-detection cost,

raw experimental artifacts, and explicit limitations.
