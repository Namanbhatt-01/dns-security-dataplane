# 2. But I see several "loop holes"

I'm going to be quite critical here because your objective isn't to make a pretty GitHub project.

You want the interviewer to think:

> **"This person actually understands network systems."**

There are several places where a strong interviewer could poke holes.

---

# LOOPHOLE #1 — Your project is called an ARM64 project, but ARM64 isn't actually the central research variable

This is probably the biggest conceptual issue.

You call it:

> `arm64-dns-security-dataplane`

and the research title is:

> "Resource-Conscious DNS Security Dataplane on ARM64 Systems"

But most of your experiments are actually about:

- matcher
- cache
- concurrency
- anomaly detection
- policy overhead
- I/O model

ARM64 is mostly the **platform**.

That's not necessarily bad.

But don't accidentally imply:

> "I researched ARM64 DNS security."

when you really researched:

> **"DNS security dataplane architecture and performance on an ARM64 Linux platform."**

The document itself correctly says to phrase results as being on the tested ARM64 platform rather than claiming ARM64 superiority.

### My recommendation

Change the conceptual positioning to:

**ARM64 Linux is the evaluation platform, not the novelty.**

That makes the project much more defensible.

---

# LOOPHOLE #2 — The cache is currently a potential security correctness hole

You have:

> cache lookup → policy → matcher → threat intelligence

in the hot path.

But your cache design says the key is:

> normalized\_domain + QTYPE + QCLASS

and stores the DNS response.  needs to be much stronger

You mention:

> response validation

and:

> transaction matching.

Good.

But I want this made explicit.

An interviewer could ask:

> "How do you know the UDP response you received is actually the response to the query you sent?"

You need a clear upstream transaction model.

At minimum define:

```
```

```
client transaction ID
        ↓
internal upstream transaction ID
        ↓
upstream source/destination
        ↓
question matching
        ↓
response validation
        ↓
client response reconstruction
```

Don't simply forward whatever comes back.

For a serious DNS dataplane, the upstream response path deserves almost as much attention as the request parser.

---

# LOOPHOLE #4 — UDP is easy; TCP DNS is where your credibility increases

Your plan puts TCP in P1.

That's correct.

But don't treat TCP as:

> "another protocol feature."

TCP DNS introduces:

- 2-byte length framing
- persistent connections
- connection lifecycle
- partial reads
- partial writes
- connection limits
- timeout behavior
- pipelining considerations
- resource exhaustion

If you implement this correctly, your project becomes substantially stronger.

### I'd actually prioritize:

**UDP → TCP → IPv4/IPv6 → concurrency**

rather than rushing toward anomaly detection.

---

Your plan already recognizes this, which I like.

Because an interviewer could absolutely ask:

> "Why Aho-Corasick?"

And if your answer is:

DNS suffix matching has semantics that aren't identical to arbitrary multi-pattern substring matching.

Your proposed experiment:


with latency, memory, build and update measurements is much better.

### My recommendation

Make the **suffix trie the expected production structure**.

Make Aho-Corasick a research candidate.

Then the strongest possible result could actually be:

> "We evaluated Aho-Corasick and rejected it."

That is much more impressive than forcing it into the architecture.

Your document already understands this principle.

**Yes. Very good.**
